# 爬虫工具（工作名 Beacon）

> 一个在本机运行的独立采集工具：把公开的官方数据变成「可审核的内容变更候选」，并保证这些变更必须通过既有门禁才能进入内容库。

## 这个目录里有什么

| 文件 / 目录 | 作用 | 状态 |
|---|---|---|
| **`PRD.md`** | **需求源**：用途、信息源、筛选规则、与 App 的接入方式、独立工具要求、验收标准 | ✅ 已评审 · 决策冻结 |
| `方案论证.md` | 为什么这么选：三方案对比、数据源可行性调研、能力边界论证 | ✅ 留档 |
| **`开发计划.md`** | WBS（32 个工作包 / 6 组）、阶段门禁（P-C1 ~ P-C5）、测试计划、里程碑、风险 | ✅ 已交付 |
| `docs/数据源清单.md` | 每个数据源的实测记录（源准入的依据） | ⏳ P-C1 产出 |
| `docs/数据契约.md` | Observation / Feed 的 JSON Schema 与版本说明 | ⏳ P-C4 产出 |
| `beacon/` | 工具本体：`core/`（源无关）+ `sources/`（数据源适配器）+ `consumers/`（目标 app 适配器） | ⏳ P-C2 起逐步产出 |

**当前进度**：P-C0 决策冻结 ✅ → **P-C1 接口可行性验证 ← 下一步**

**首版范围**：4 个指标（PMI、社融、收益率曲线、估值分位），14 个后续指标/概念移入 v1.1。详见 `开发计划.md` §1.2。

## 三条边界（一句话版）

1. **只服务世界热点** —— 经济学与金融学的内容靠理解与表达，不靠采集
2. **只采数值与事实** —— `key_points`、因果解读、分歧观点、`recipe` 组合永远由人写
3. **不直连 App** —— 产出仍是 `content/*.yaml`，走既有门禁与发布链路；App 侧零改动

## 文档体系中的位置

```
acknowledge/                     ← Recall（App）项目
├─ PRD.md / 架构设计.md / ...      App 的需求、架构、交互
└─ 爬虫/                          ← 本工具（独立目录、独立依赖、独立版本）
   ├─ PRD.md                      ★ 本工具的需求源
   ├─ 方案论证.md                   为什么这么选
   └─ beacon/                     （后续）工具本体
```

**规则**：需求变更只改 `PRD.md`。`方案论证.md` 与 `开发计划.md` 不得重新定义需求。

## 关于「独立」

| 维度 | 独立性 |
|---|---|
| **仓库** | **独立 Git 仓库**：`Ramon7Ruan/RAMON-project-crawler`（2026-09-28 从 App 仓库拆出）。本目录有自己的 `.git`，与 App 各自提交、互不感知 |
| 目录 | `爬虫/`，不散落到 App 的 `app/`、`src/`、`tools/` |
| 依赖 | 自己的依赖清单与虚拟环境，**不进入 App 的 `node_modules`** |
| 运行 | 不依赖 Node/npm，不依赖 App 已安装 |
| 版本 | 独立版本号，与 App 各自演进 |
| 路径 | 全部通过参数/配置传入，**不硬编码父项目相对路径** |
| 复用 | `feed.jsonl`（中性产物）可被任意 app 读取；新增 app 只需加一个 `consumers/` |

详见 `PRD.md` §6。

### 在独立仓库里跑测试

```bash
cd beacon && python -m pytest -q
```

默认会 **196 通过 / 2 跳过**。跳过的是 `tests/test_consumers.py` 里那两条
「对真实内容库做往返验证」的断言——它们需要一个**真实内容库**才能跑，
而本仓库不含 App 的 `content/`（那是 App 的资产）。它们会明确跳过，
而不是静默通过：跑不了就说跑不了，这是这个项目的一贯做法。

要跑满 198 项，把内容库路径告诉它：

```bash
RECALL_CONTENT_DIR=/path/to/acknowledge/content python -m pytest -q
```

> 这两个断言只在**维护本工具本身**时值得跑；日常改指标配置不需要它们。
